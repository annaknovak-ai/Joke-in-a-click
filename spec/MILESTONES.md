# MILESTONES — בדיחה בלחיצה

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md` (והתמונות `wireframes.png`, `style-guide.png`, `mockups.png`).

## עקרונות מנחים

- הפיתוח מיועד למסך מובייל אחד בלבד, בעברית וב-RTL, ללא תפריט או מסכים נוספים.
- מימוש לפי ה-Technology Stack שנבחר: React, TypeScript, Vite, CSS, Vercel Function, OpenAI Responses API במודל `gpt-5`, ו-`vite-plugin-pwa`.
- אין Database, Authentication, שמירת היסטוריה או Rate Limiting של המוצר.
- כל Milestone מסתיים בתוצר שניתן להריץ ולבדוק. רכיבי תשתית המוקמים לפני חיבור ה-AI לא יוצגו למשתמש כיכולת שכבר עובדת.
- ה-PRD גובר על רכיבים דקורטיביים סותרים בתמונות; בפרט אין לממש את אייקון התפריט שמופיע בחלק מה-Mockups.

## Milestone 1 — הקמת פרויקט ומסך ראשי ✅

**שם ומטרה:** לבסס אפליקציית מובייל ניתנת להרצה עם המסך היחיד ועיצובו, לפני חיבור לשירות ה-AI.

**מה יש לממש:**
- יצירת פרויקט React + TypeScript עם Vite, תשתית CSS, וסידור Repository יחיד עבור Frontend ו-Backend בהמשך.
- מימוש מסך **"בדיחה בלחיצה"** בהתאם למבנה ה-Wireframes ולעיצוב ה-Style Guide וה-Mockups: כותרת, שדה נושא, לחצן **"צור בדיחה"** ואזור להצגת בדיחה.
- ממשק RTL בעברית, צבעי המותג (כולל Strong Pink לכפתור), טיפוגרפיה, רכיבים מעוגלים ופריסת עמודה אחת.
- איתור צילום חתלתול חופשי לשימוש, שמירתו בפרויקט ותיעוד המקור והרישיון.
- קובצי הגופנים Heebo ו-Assistant נכללים בפרויקט ואינם נטענים מ-Google Fonts.
- הטקסטים לפי DESIGN: "על מה תרצה בדיחה?", טקסט הדוגמה בשדה, ומצב ריק בכרטיס: "הבדיחה תופיע כאן לאחר הלחיצה".
- שדה נושא אופציונלי המוגבל ל-100 תווים, עם מונה תווים `0/100`.
- הגדרת תצוגת טקסט אזור הבדיחה כך שתתמוך גם בתוכן LTR ותוכן ארוך, ללא גלילה אופקית.
- עד לחיבור השירות, אין להציג בדיחות שמתחזות לתוצאה של GPT-5; הכפתור יישאר לא פעיל או יסומן בבירור כפונקציונליות שטרם חוברה בסביבת הפיתוח.

**תוצר מצופה:** אתר מובייל מקומי הנפתח ומציג מסך מעוצב ותקין; ניתן להזין ולערוך נושא, אך טרם ניתן להפיק בדיחה אמיתית.

**Definition of Done:**
- הפרויקט מותקן, נבנה ללא שגיאות TypeScript ונטען מקומית.
- כל ארבעת הרכיבים המרכזיים מופיעים במסך יחיד, בפריסה הדומה למקורות העיצוב וללא תפריט ניווט.
- הממשק בעברית ו-RTL; הזנת 100 תווים מתאפשרת, ותו 101 אינו מתקבל; מונה התווים מתעדכן.
- תצוגת המובייל אינה גורמת לגלילה אופקית, וניתן לבדוק בה טקסט ארוך בשלב הפיתוח.
- אין מפתחות API או סודות בקוד הלקוח או ב-Repository.

## Milestone 2 — יצירת בדיחה מקצה לקצה ✅

**שם ומטרה:** לספק את ה-Vertical Slice המרכזי: הזנת נושא, יצירת בדיחה חדשה ב-GPT-5 והצגתה באותו מסך.

**מה יש לממש:**
- Vercel Function ב-TypeScript עבור `POST /api/joke`, כולל אימות קלט בצד השרת, טיפול בנושאים ריקים/רווחים והחזרת JSON לפי חוזה ה-API שב-ARCHITECTURE.
- שימוש ב-OpenAI SDK וב-Responses API עם המודל `gpt-5` ברמת חשיבה מינימלית; יצירת בדיחה בנושא שהוזן ובשפתו, או בדיחה כללית בעברית כשהנושא ריק; בדיחות מתאימות לכל גיל ולא פוגעניות; ללא הגדרת סגנון או אורך קשיחים.
- שימוש ב-`OPENAI_API_KEY` ב-Backend בלבד, מקובץ `.env` שאינו נשמר ב-Git (ועם `.env.example` ללא ערכים).
- הרצה מקומית של ה-Function דרך שרת הפיתוח של Vite, **ללא חשבון Vercel** (ADR-1); בדיקות מקומיות של ה-Function ושל ה-Frontend יחד.
- חיבור הכפתור ל-`/api/joke` באמצעות בקשה חדשה בכל לחיצה, והחלפת הטקסט בכרטיס הבדיחה ללא שמירת היסטוריה.
- תצוגת בדיחה כ-Plain Text בכיווניות המתאימה לשפת התוצאה.

**תוצר מצופה:** משתמש יכול להזין נושא או להשאיר את השדה ריק, ללחוץ על הכפתור ולקבל בדיחה אמיתית שנוצרה ב-GPT-5.

**Definition of Done:**
- בדיחה בנושא בעברית מוצגת בעברית; בדיחה בנושא באנגלית מוצגת באנגלית; שדה ריק או רווחים בלבד מפיקים בקשה לבדיחה כללית בעברית.
- נושא רגיש מפיק בדיחה שאינה פוגענית.
- שתי לחיצות עוקבות לאחר השלמת הבקשה מפעילות שתי בקשות יצירה נפרדות, והבדיחה החדשה מחליפה את הקודמת בכרטיס הקיים (ללא הבטחה ששתי תוצאות המודל תהיינה שונות).
- API דוחה קלט שאינו תקין, לרבות נושא ארוך מ-100 תווים, גם אם נשלח ישירות ולא דרך הממשק.
- ה-API מחזיר את מבני התשובה והקודים המוגדרים בארכיטקטורה, ללא Cache של בדיחות.
- המפתח אינו מופיע ב-Bundle של ה-Frontend, בבקשות שיוצאות מהדפדפן או בתגובות ה-API.
- נבדקה גישה ממשית ל-`gpt-5`; אם אינו זמין לחשבון, עוצרים ומציגים למשתמש את החסימה — לא מחליפים מודל על דעת עצמנו.

## Milestone 3 — חוויית שימוש שלמה והפעלת PWA ✅

**שם ומטרה:** להפוך את זרימת יצירת הבדיחה לאמינה וברורה במצבי טעינה, כשל וניתוק, ולאפשר התקנה ופתיחה Offline.

**מה יש לממש:**
- הצגת **"מכין לך בדיחה..."** בתוך כרטיס הבדיחה בזמן בקשה, השבתת כפתור היצירה במהלך ההמתנה ומניעת שליחת בקשות מקבילות מאותו לחצן.
- טיפול בשגיאות רשת, כשל Backend או שירות OpenAI, והצגת הודעה בעברית מתחת לכפתור, כשהבדיחה הקודמת נשארת בכרטיס. לאחר כשל ניתן לנסות שוב באותו כפתור, ללא Retry אוטומטי שעלול להפיק חיוב כפול.
- הצגת **"נדרש חיבור לאינטרנט כדי ליצור בדיחה"** כשהמכשיר מדווח שאין חיבור או כשהבקשה לא הגיעה לשרת, תוך שמירה על זמינות מעטפת הממשק.
- הגדרת `vite-plugin-pwa`, Web App Manifest (כולל `theme_color` ‏Blush Pink), אייקונים מצילום החתלתול, Service Worker ו-Caching של קובצי המעטפת, התמונה והגופנים בלבד. אין לשמור תשובות בדיחה במטמון או באחסון מתמשך.
- בדיקת גלילה לקריאת בדיחות ארוכות ושימור פריסת מובייל, **במחשב בהדמיית טלפון**. בדיקות בטלפון אמיתי מתבצעות באבן דרך 4.

**תוצר מצופה:** האפליקציה מוכנה לשימוש ולהתקנה כ-PWA, עם חיווי ברור במצבים הרלוונטיים ויכולת לפתוח את הממשק בלי אינטרנט לאחר טעינה/התקנה מוצלחת.

**Definition of Done:**
- בזמן יצירה ההודעה הנכונה גלויה ולא ניתן להפעיל בקשה נוספת באמצעות הכפתור; בסיום הבקשה הכפתור חוזר להיות זמין.
- כשל API/רשת מוצג בעברית; ניתן להפעיל ניסיון חוזר ולקבל בדיחה כאשר השירות חוזר לעבוד.
- לאחר שהאפליקציה נטענה ברשת ונכסי המעטפת נשמרו, ניתן לפתוח אותה ללא חיבור; ניסיון יצירה במצב זה מציג את הודעת ה-Offline ולא יוצר בדיחה.
- מתקיימים התנאים הטכניים להתקנת PWA ב-Chrome (Manifest, אייקונים, Service Worker), כפי שנבדק במחשב. ההתקנה בטלפון אמיתי נבדקת באבן דרך 4.
- בדיחות ונתוני נושא אינם נשמרים כנתונים עסקיים בין הפעלות, ותגובות `/api/joke` אינן נשמרות במטמון.
- מראה המצבים נשאר באותו מסך, ללא מודאלים/תפריטים/דפים חדשים.

## Milestone 4 — פריסה אוטומטית ובדיקת Production ✅

**שם ומטרה:** לפרסם אפליקציה עובדת בכתובת HTTPS ולהבטיח שינויים עתידיים נפרסים אוטומטית מתוך GitHub.

**מה יש לממש:**
- חיבור ה-Repository הקיים ב-GitHub (`annaknovak-ai/Joke-in-a-click`) לפרויקט Vercel יחיד (תוכנית Hobby), עם Frontend סטטי ו-`api/joke` כ-Node.js Function באותו Origin. המשתמשת פותחת את החשבון ומחברת אותו בעצמה, בהדרכה צעד אחר צעד.
- הגדרת `OPENAI_API_KEY` כ-Environment Variable סודי ב-Vercel Production; מפתח אחד, ללא סביבת Preview (ADR-4). אין לכלול מפתחות בקוד או ב-Git.
- הגדרות Build של Vite ופריסה אוטומטית מ-`main` ל-Production. לפני כל Push ל-`main` נדרש אישור מפורש של המשתמשת.
- הגדרת תקרת הוצאה חודשית והתראת תקציב בחשבון OpenAI, על ידי המשתמשת בהדרכה.
- בדיקות קבלה בכתובת HTTPS אמיתית בדפדפן Chrome על Android ועל iPhone, כולל RTL, יצירת בדיחה, שגיאות, התקנת PWA והתנהגות Offline בהתאם לאפשרויות מערכת ההפעלה.
- בדיקת הגדרות האבטחה, תגובות ללא Cache, זמינות Endpoint, וסיכוני העלות של שירות ציבורי פתוח ללא מכסת שימוש; אין להוסיף Rate Limiting בניגוד ל-PRD.

**תוצר מצופה:** האפליקציה זמינה לציבור ב-Vercel, ניתנת להתקנה במכשירים שבהם Chrome והמערכת תומכים בכך, וניתנת לעדכון באמצעות Push ל-GitHub.

**Definition of Done:**
- כתובת Production עם HTTPS מציגה את המסך היחיד וה-API פועל באותו Origin.
- בדיקות הקבלה של Milestones 1–3 עוברות בסביבת Production, לרבות שגיאות, נושא ריק, התאמת שפה והחלפת בדיחה קיימת.
- אין חשיפה של `OPENAI_API_KEY` ל-Frontend, ל-Repository או לתגובות API; הסוד קיים רק בהגדרות שרת מקומיות/Hosting כנדרש.
- עדכון מאושר ב-`main` מוביל אוטומטית ל-Production Deployment תקין ללא פעולה ידנית לפריסה.
- הוגדרו תקרת הוצאה והתראת תקציב בחשבון OpenAI.
- נבדקו התקנה ופתיחה Offline במכשירים הנתמכים בפועל, ותועדו מגבלות אפשריות של Chrome ב-iPhone מבלי להבטיח זהות מלאה ל-Android.
- הובהר למשתמש ששימוש ב-OpenAI וב-Vercel עלול להיות כרוך בחיובים, במיוחד ללא מכסת שימוש; ניטור תפעולי אינו יוצר מגבלת מוצר חדשה.

## Development Execution Rules — הוראות מחייבות ל-AI המבצע

1. **יש לפתח את ה-Milestones אך ורק לפי הסדר המתואר במסמך.** כל שלב נשען על התוצר שעבר בדיקות בשלב שקדם לו.
2. **בסיום כל Milestone יש לעצור את הפיתוח**, להציג למשתמש מה מומש, כיצד ניתן להפעיל ולהתנסות בתוצר, ואת תוצאות הבדיקות מול **כל** סעיפי ה-Definition of Done; יש לציין במפורש כשלים, מגבלות או בדיקות שלא ניתן היה לבצע.
3. **אין להתחיל את ה-Milestone הבא בלי אישור מפורש של המשתמש**, גם אם כל הבדיקות עברו.
4. אין להוסיף פיצ'רים, לשנות מודל AI, להוסיף Database או לשנות דרישות מוצר בניגוד ל-PRD ללא אישור מפורש.
